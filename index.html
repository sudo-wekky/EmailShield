How the score works

Every rule carries a fixed point value and a severity. Points are summed per category and clamped to that category's cap, heaviest findings first, then the category subtotals are summed and clamped to 100. That is why a message with eleven bad links cannot outweigh everything else.

Step 1

Analyzers emit signals

Five analyzers run over the parsed message. Each is a pure function with no network, storage or filesystem access, so a crafted email cannot make one act on its behalf.

Step 2

Categories are capped

Sender 35 · Authentication 30 · Links 40 · Attachments 30 · Content 25 · Headers 15. Language alone can never push a message past the Suspicious band.

Step 3

The total is banded

The capped total maps to one of four bands, each with a recommended action written for a person deciding what to do next — not for a filter.

Risk bands

a risk score, not a probability
Low Risk0 – 24 No major indicators found.
Suspicious25 – 49 Review the sender and links before interacting.
High Risk50 – 74 Verify through a channel you already trust.
Critical Risk75 – 100 Do not interact; report it.

A score of 80 does not mean "80% likely to be phishing". It means the message accumulated 80 points of weighted indicators. EmailShield never states a probability, because it has no basis for one.

What it looks for

44 rules across six categories. Every one of them explains itself in the report: what was observed, the evidence from the message, and why it matters.

Sender · 9 rules · cap 35

Does the identity shown match the identity sent from?

Display names containing a different address or claiming a brand the domain doesn't back; lookalike domains; Reply-To and Return-Path mismatches; internal-looking mail that failed authentication; consumer webmail used for business requests. Lookalike detection folds confusable characters (0↔o, rn↔m, 1↔l) to a skeleton and applies a bounded edit distance, so both micros0ft-verify.example and examp1e.com are caught.

Authentication · 6 rules · cap 30

What did the receiving server conclude?

SPF, DKIM and DMARC verdicts read from Authentication-Results, falling back to Received-SPF. Hard failures score more than soft ones. A message with no results is reported as unknown rather than treated as a pass — absence of evidence is not evidence.

Links · 13 rules · cap 40

Where would this actually take you?

Link text that shows one address and points at another; raw IPs including decimal and hex forms; punycode hosts; shorteners; lookalike domains; a brand used as a subdomain of somewhere else; user@host obfuscation; odd ports; suspicious encoding; sign-in pages over plain HTTP; direct downloads; javascript: and data: schemes.

Message content · 8 rules · cap 25

Is it working on you?

Urgency, credential requests, threatened consequences, financial and gift-card lures, authority impersonation. Each family needs a multi-word phrase or corroboration before it fires, so an ordinary message containing the word "urgent" stays quiet. Plus forms that collect passwords, and text hidden with display:none or zero font size.

Attachments · 5 rules · cap 30

What is attached, and what would open it?

Dangerous extensions, double extensions like invoice.pdf.exe, macro-capable Office formats, HTML attachments, archives. Metadata and SHA-256 only — nothing is opened, extracted or executed, and the report says Malware scanning: Not configured because there is no scanner.

Headers · 3 rules · cap 15

Does the delivery story hold together?

No Received chain at all; a Re: subject with no In-Reply-To or References, the usual sign of a fake reply; a Message-ID issued by a different domain than the sender.

Handling hostile input

Every file this page is given is, by definition, something somebody already suspected was an attack. Three things follow from that.

1 · No URL is ever requested

A phishing analyser is an obvious target for server-side request forgery: it is handed attacker-chosen URLs and might plausibly want to check them. EmailShield doesn't. Links are parsed as strings and analysed structurally. No fetch, no DNS lookup, no reputation API, no preview request. The cost is that a shortened link's destination cannot be resolved — which the report states plainly rather than guessing.

2 · The message body is rendered inert

An allowlist sanitiser rebuilds the document from scratch. Tags that can carry behaviour — script, style, iframe, object, form, svg and the rest — are dropped with their contents. Every attribute outside a short layout allowlist is discarded, which removes every on* handler without enumerating them. <img> is removed entirely so tracking pixels cannot fire and confirm the message was read. href is stripped and the destination printed as text beside the link, so nothing in a preview is one click from anywhere.

The result is then rendered in an iframe with sandbox="", which gives it an opaque origin: even if sanitisation were bypassed completely, the browser refuses to run script in it.

3 · Nothing leaves your browser

This page has no backend. The file is read with FileReader, parsed, analysed and rendered locally; it is never uploaded anywhere, including to whoever is hosting this page. The only thing stored is a short list of filenames and scores in this browser's own localStorage, which you can clear with the button above.

The full application

Python · Flask · SQLite

This page is a browser port of a server application built for internal deployment. That version adds what a browser cannot do: single sign-on, per-user isolation and an audit trail.

  • Authentication. OpenID Connect, Authorization Code flow with PKCE. The ID token is checked for signature against the provider's JWKS, issuer, audience, expiry and nonce before any session exists. No passwords are stored, requested, or possible — there is no password column in the schema.
  • Authorization. Ownership is scoped in the SQL WHERE clause, not compared after the fetch. A report belonging to someone else returns the identical 404 as one that doesn't exist, so identifiers can't be probed. Administrators get statistics and the audit trail — not other people's correspondence.
  • Uploads. Extension allowlist, size limit enforced before parsing, and a content sniff that rejects a renamed executable. Files are written with O_EXCL and mode 0600 under a random name, in a directory outside the web root.
  • Retention. Message content is deleted after 24 hours. The score, band and rule IDs survive, so history stays meaningful without holding anybody's correspondence.
  • Audit trail. Sign-ins, analyses and report views are recorded. Client addresses are stored as a truncated keyed HMAC, never in the clear, and no message content is ever written to the log.
  • Tests. 178 of them, including attacks on the auth flow — forged signature, alg=none, replayed authorization code, wrong audience, missing nonce — and on object ownership, CSRF and path traversal. One replaces the socket constructor with a function that raises, then runs the URL analyzer, to prove no link is fetched.

What it can't do

This is decision support for a person, not an automated verdict. Being straight about the edges is part of the tool working properly.

  • Headers can be forged. SPF, DKIM and DMARC verdicts come from a header the receiving mail server added. EmailShield cannot verify DKIM signatures itself, because that depends on the receiving server's view of the message. A message exported from a mailbox whose gateway adds no such header is reported as unknown.
  • False positives are expected. Marketing platforms wrap links in tracking redirectors, which look exactly like link-text mismatches. A newsletter from a mailing service will often land in the Suspicious band. Every finding is explained precisely so you can dismiss one on the evidence.
  • False negatives are expected. A well-crafted, authenticated, plain-text message from a genuinely compromised account may score zero. Nothing here detects a real account that has been taken over.
  • No malware analysis. Attachments are hashed and classified by extension. A malicious PDF is invisible to this tool.
  • No threat intelligence. No domain reputation, no blocklists, no sandbox detonation. Both of these are reported as Not configured rather than quietly omitted, so the report never implies a check that didn't happen.
  • Registrable domains are approximated. A small built-in suffix table stands in for the Public Suffix List, so unusual TLDs may split incorrectly and affect lookalike comparisons.
  • Language rules are English-only. Phishing in another language won't trip the content rules, though every structural rule still applies.

EmailShield analyses email structure and language. It does not guarantee that a message is safe, and it produces both false positives and false negatives. Treat the score as one input to your own judgement — and when something feels wrong, verify with the sender through a channel you already trust.

Sample messages are synthetic. Every domain in them is a reserved example domain and every IP address is from a TEST-NET range, so nothing in them resolves to a real host.
